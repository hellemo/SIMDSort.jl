AVX-512 notes

SIMDSort.jl was developed and measured on an AVX2 laptop (Intel Core Ultra 7 268V). This file lists what changes on an AVX-512 machine, what the code already does about it, what was measured on an AVX-512 server, and how to measure on another one.

What changes on AVX-512, and what the code does

AspectAVX2 (measured)AVX-512In the code
Vector registers1632The 32-row base-case networks are split into two 16-row halves only without AVX-512 (sortnet, src/network.jl).

Partition stepvpartition: permutation table + vpermdsame (SIMD.jl keeps the table for 2/4/8 lanes)Unchanged: native vpcompress (Bramas 2017) measured no faster at 256 bits (bench/avx512.jl part).
Vector width256-bit512-bit512 bits with AVX-512 (vecbits(), src/network.jl): the partition and scan kernels use 512-bit vectors, the partition steps a native compress to the left and a compress-store to the right (on AMD Zen a compress into a register and a masked store instead, see below), and the full base case 16 rows of 512 bits instead of 32 of 256 (same keys; smaller leaves keep the 256-bit networks). VEC_BITS forces a width; the test matrix runs the 512-bit code on AVX2.
Unsigned 64-bit compare, min/maxnone (keys are mapped to signed, two passes)native (vpcmpuq, vpminuq)UInt64 is sorted as is with 512-bit vectors (keyclass).
Tuning constantsunroll 8, prefetch 512 keys ahead above 2 MB, 32-row base casedifferent caches (e.g. 1–2 MB L2)Unchanged; worth re-measuring.

The first two rows are decided when the code is compiled, from SIMD.Targets.has_feature (host CPU, -C native). On AVX-512 they select code paths that are tested on AVX2 as well: the single 32-row network, and the integer networks.

Results on a 2 × 28-core Xeon Gold 6348 (Ice Lake-SP)

Two sockets, 56 cores, two NUMA nodes, full AVX-512 (incl. VBMI2), 1.25 MB L2 per core; one core copies about 13 GB/s, all cores about 140 GB/s.

  • All tests pass with the AVX-512 code paths.
  • The machine code confirms the decisions above: the Int64 networks use vpminsq/vpmaxsq without blends, and the single 32-row networks spill far less than on AVX2 (98 stack loads against 205). No zmm register is used.
  • 32-row network, single against two halves: 167 against 208 ns (Int32), 140 against 166 ns (Float64): the single network is right for AVX-512.
  • Native compress against the permutation table: no gain at 256 bits.
  • One thread with 256-bit kernels: 7–25% behind vqsort and x86-simd-sort (Int64 2^26: 0.79 s against 0.68 and 0.73 s); in-cache partitions (about 0.35 ns/key for Int64) and the leaves dominate, both limited by the vector width. Hence the 512-bit path below.
  • Many threads: the parallel quicksort stops scaling at about 16 threads; the sample-sort top level (design.md §7.j) keeps scaling.
  • Tuning constants: none changed alone gains more than about 2%.

The 512-bit path (measured with bench/ab.jl, the same code at VEC_BITS = 256 as baseline; bench/measure/abphases.jl for the phases):

At 56 threads the times are within noise (memory bound). Where the gain comes from: in-cache partitions 17–18% faster for the integer types, and the Int64 base case 24% (its 256-bit networks were slow: 32 rows spill, 16 rows of 512 bits do not). Unroll 4 at 512 bits (the same bytes per step as 8 at 256) was 4–5% slower than 8.

Floats gain little because of the clock. Sorted as integer keys (the same data, bench/measure/floatkernels.jl), Float64 at 512 bits takes 0.160 s against 0.167 s through the float kernels: its scalar pivot code is 18% faster and the partitions 10%, as when the core keeps a higher clock without 512-bit floating-point instructions; the integer networks are slower than the float ones, so the net difference is 4.5% (Float32: 1%). Possible follow-up: sort floats through the integer kernels on AVX-512, mapping the keys in registers (partition compares, pivot, networks, scalar tails), for those 4.5%.

One thread against x86-simd-sort (bench/measure/scaling.jl): UInt64 2^27 1.445 against 1.485 s (was 1.820 with 256-bit kernels and the key map), Int64 2^26 0.704 against 0.738 s (was 0.795), Int32 0.357 against 0.347 s (was 0.372), Float64 0.754 against 0.675 s (unchanged). At 56 threads, where the sample-sort step runs, the dropped key map also helps UInt64 2^27: 0.102 s against 0.150 before and 0.116 for ChapelSort's radix sort, so SIMDSort now leads every case of the scaling set there.

AMD Zen 4: the memory compress-store

The first report from a Zen 4 machine (an AMD EPYC 9274F, issue #1) showed the 512-bit sort several times slower than expected: 0.61 s for 2^24 Int64 on one thread, 0.58 s of it partitioning, about 1.8 ns per key and partition level (the Ice Lake Xeon above: about 0.3 ns). The partition wrote its right side with SIMD.jl's vstorec, which on AVX-512 is LLVM's compressstore, the memory form vpcompressq [mem]. That form is reported to be microcoded and very slow on Zen 4, while the register form of vpcompress and masked stores are fast; it also fits the reporter's finding that x86-simd-sort is fastest there when built for Haswell (without AVX-512).

On AMD Zen (LLVM CPU name znver*) the kernels therefore compress into a register and store masked to the kept lanes (vstc, src/keyref.jl). Not on Intel: on the Ice Lake Xeon that form is 8-11% slower than the memory form on one thread (2^24 keys; about 1-1.7 ms more per partition level, SortBench-Idun steps abvstc phasesvstc), so the memory form stays the default there. VSTC_MEMORY = true/false forces either. Confirmation on Zen 4 is pending; for Zen 5 there is no data.

Measuring on an AVX-512 machine

The scripts below run on any machine and write their results to $OUT (default: bench/measure/results/). They use the lean environment bench/measure/Project.toml (no plotting packages, quick to install on a server); tables and charts are made with the bench/ environment from the CSV files. The comparison sorts need the C++ shim built on the machine itself (ChapelSort.jl/bench/simd/build.sh, -march=native).

julia --project=bench/measure -e 'using Pkg; Pkg.instantiate()'
julia --project=bench/measure bench/measure/env.jl              # CPU, features, code paths, caches, bandwidth
julia --project=bench/measure bench/measure/codegen.jl          # machine code of the hot kernels
julia -t auto --project=bench/measure bench/avx512.jl all       # kernels, 512-bit experiment, full sorts
julia -t auto --project=bench/measure bench/measure/instrument.jl   # phase times and counters
julia -t auto --project=bench/measure bench/measure/scaling.jl      # thread scaling
julia -t auto --project=bench/measure bench/measure/distcross.jl   # quicksort vs sample-sort step
julia -t auto --project=bench/measure bench/measure/tune.jl         # tuning constants

SIZE_LOG sets 2^k keys for the instrument, scaling and tune scripts (default 26). bench/profile.jl and the README comparisons (bench/bench.jl, types.jl, crossover.jl, which write to $BENCH_RESULTS if set) complete the picture.

Reading the results

  • The AVX-512 decisions: codegen.csv shows whether the Int64 networks use vpminsq (no blends) and whether the 32-row networks still spill; avx512.jl measures the alternatives directly.
  • Where the time goes: instrument.csv gives task time per phase. Compare the partition_2e* rows with leaf_sort and pivot across thread counts: partition costs that grow with the thread count point to memory bandwidth, costs that stay the same to compute. High gc_ns points to allocations.
  • The sample-sort crossover: in scaling.csv, "SIMDSort dist" against "SIMDSort quicksort" shows from which thread count the top level should be used; distcross.csv the full crossover over size and tasks (use_distribution in src/msd.jl).
  • Retuning: tune.csv. A constant whose change wins in several cases by more than the spread between rounds is worth changing (behind the AVX-512 check if it loses on AVX2).
