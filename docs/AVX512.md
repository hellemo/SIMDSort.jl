# AVX-512 notes

SIMDSort.jl was developed and measured on an AVX2 laptop (Intel Core Ultra 7
268V). This file lists what changes on an AVX-512 machine, what the code already
does about it, and how to measure the rest, e.g. on an NTNU Idun node.

## What changes on AVX-512, and what the code does

| Aspect | AVX2 (measured) | AVX-512 | In the code |
|---|---|---|---|
| Vector registers | 16 | 32 | The 32-row base-case networks are split into two 16-row halves only without AVX-512 (`sortnet`, `src/network.jl`). |
| 64-bit integer min/max | compare + two blends | native `vpminsq`/`vpmaxsq` (also on 256-bit vectors, AVX-512VL) | Int64 leaves are sorted as Float64 offsets (`leaf_sort!`, `src/sort.jl`) only without AVX-512. |
| Partition step | `vpartition`: permutation table + `vpermd` | same (SIMD.jl keeps the table for 2/4/8 lanes) | Unchanged. Native `vpcompress` (Bramas 2017) might be faster on recent cores: measured by `bench/avx512.jl part`. |
| Vector width | 256-bit (`lanes(T) = 32 ÷ sizeof(T)`) | 512-bit possible | Kept at 256 bits. 512-bit vectors would need the AVX-512 float min/max intrinsics in `vmin`/`vmax`, and re-tuning; some Intel parts clock down under 512-bit instructions. |
| Tuning constants | unroll 8, prefetch 512 keys ahead above 2 MB, 32-row base case | different caches (e.g. 1–2 MB L2) | Unchanged; worth re-measuring. |

The first two rows are decided when the code is compiled, from
`SIMD.Targets.has_feature` (host CPU, `-C native`). On AVX-512 they select code
paths that are tested on AVX2 as well: the single 32-row network, and the integer
networks.

## Running the measurements on Idun

Everything is in `bench/idun/`. One job runs all measurements and writes them
to one results directory, so that weak spots can be found afterwards without
access to the machine.

```sh
# 1. Here: copy the sources (this repo, ChapelSort.jl, the SIMD.jl fork) to
#    ~/sortbench on Idun via the ssh alias idunpw (IDUN_HOST overrides it).
bench/idun/sync_to_idun.sh

# 2. On the login node (needs internet): packages, precompilation, and the
#    C++ comparison sorts (x86-simd-sort, vqsort) built with -march=native.
#    Julia: `module load Julia` if available, else juliaup in $HOME.
ssh idunpw
cd sortbench/SIMDSort.jl
bash bench/idun/run.sh setup build

# 3. Set --account (and --partition or --constraint for an AVX-512 node) in
#    the job file, then submit; about 2-4 hours on a whole node.
sbatch bench/idun/job.slurm             # or: sbatch bench/idun/job.slurm instrument scaling

# 4. Here, when it is done:
bench/idun/fetch_results.sh             # into bench/idun/results/ (git-ignored)
```

The run uses its own lean environment, `bench/idun/Project.toml`, with no
plotting packages (CairoMakie has caused trouble on Idun), and a dedicated
package depot (`/cluster/work/$USER/julia_depot`, else `~/sortbench_depot`;
`SORTBENCH_DEPOT` overrides it), so a personal `~/.julia` with private
registries is never touched. Tables and charts are made here from the fetched
CSV files: copy them into `bench/results/` and run `bench/tables.jl` and
`bench/plots.jl`.

Note that `-march=native` must match the compute node: if the login node has a
different CPU, run the `build` step inside the job instead
(`sbatch bench/idun/job.slurm build codegen ...`, or all steps).

### What a run records

`bench/idun/run.sh [steps]` writes `bench/idun/results/<host>-<time>/` and a
tarball of it. `steps.tsv` gives each step's exit status and duration; each step
also has its own `<step>.log`, and a failed step doesn't stop the others.

| Step | Output | What it answers |
|---|---|---|
| `env` | `system.txt`, `julia_env.txt` | CPU model, `lscpu`, NUMA layout, caches, governor, AVX-512 subsets; the features SIMD.jl detects; which code paths were compiled (Int64 leaves as doubles, split networks), lanes and base-case sizes, tuning constants; copy bandwidth at 1 and all threads; git commits |
| `test` | `test.log` | correctness of all code paths on this CPU |
| `codegen` | `codegen.csv`, `asm/*.s` | per kernel and type: instruction count, zmm/ymm use, `vpcompress`, permutes, native `vpminsq`/`vpmaxsq`, blends, mask registers, stack loads and stores (spills in the 32-row networks) |
| `avx512` | `avx512.log`, `avx512_wide.csv` | partition step with table + `vpermd` vs native compress; 32-row network as one vs two halves; full sorts vs x86-simd-sort and vqsort; the 512-bit experiment (section 4): partition and network kernels at 256 and 512 bits, per key |
| `instrument` | `instrument.txt`, `instrument.csv` | per case at 1, NT/4 and NT threads: phase times (key map, counting/hash checks, pivot, partitions by size class 2^k, leaves, MSD and distribution phases, window sorts), counters (partition calls and keys per level, three-way partitions, depth-limit fallbacks, bucket sizes, spawned tasks), and plain vs instrumented wall time |
| `profile` | `profile.log` | statistical profile shares, partition cost per key by range size with and without prefetch, base-case cost |
| `scaling` | `scaling.csv` | time by thread count (1, 2, 4, … all) for SIMDSort, its sample-sort top level for 64-bit keys (disabled by default), ChapelSort and x86-simd-sort |
| `tune` | `tune.csv`, `tune.log` | each tuning constant changed alone (unroll, prefetch distance and threshold, task grain, parallel-partition threshold, big-pivot threshold, network rows, zigzag), relative to the committed values |
| `bench`, `types`, `crossover` | `bench.csv`, `types.csv`, `crossover.csv` | the README comparisons on this machine |

Environment variables: `NT` (threads, default all CPUs of the job), `OUT`
(results directory), `ROUNDS`, `QUICK=1` (fewer rounds and smaller sizes, for a
first check that everything runs), `SIZE_LOG` (2^k keys in the instrument,
scaling and tune steps; default 26).

### Reading the results

* **The AVX-512 decisions:** `codegen.csv` shows whether the Int64 networks use
  `vpminsq` (no blends) and whether the 32-row networks still spill. The
  `avx512` step measures the alternatives directly.
* **Where the time goes:** `instrument.csv` gives task time per phase. Compare
  the `partition_2e*` rows with `leaf_sort` and `pivot` across thread counts.
  Partition costs that grow with the thread count point to memory bandwidth;
  costs that stay the same point to compute.
* **The 64-bit thread gap:** in `scaling.csv`, "SIMDSort dist" against
  "SIMDSort" shows whether the sample-sort top level should be enabled
  above some thread count (`DIST_MINN`, `DIST_MINTASKS` in `src/msd.jl`).
* **Retuning:** `tune.csv`. A constant whose change wins in several cases by
  more than the spread between rounds is worth changing (behind
  `has_avx512()` if it loses on AVX2).
